# Race Conditions и Решения для Loggy

## 🔍 Потенциальные проблемы

### 1. Race Condition при создании лога и WebSocket broadcast

**Проблема:**
```
Время | Поток 1 (HTTP)          | Поток 2 (WebSocket)
------|-------------------------|----------------------
T1    | Создан лог в БД         |
T2    |                       | Клиент подписывается
T3    | Broadcast лога        | (подписка еще не активна)
T4    |                       | Лог не получен! ❌
```

**Сценарий:**
1. Лог сохранен в БД
2. Пытаемся отправить через WebSocket
3. Клиент подписывается ПОСЛЕ того как лог уже был обработан
4. Клиент пропускает лог

**Решение:**
- ✅ **Не критично для реалтайм:** Реалтайм логи - это новые логи ПОСЛЕ подписки
- ✅ **История доступна:** Клиент всегда может запросить историю через REST API
- ✅ **Опционально:** При подписке отправлять последние N логов (например, последние 100)

### 2. Race Condition при проверке доступа к проекту

**Проблема:**
```
Время | Поток 1 (WebSocket)     | Поток 2 (HTTP)
------|-------------------------|----------------------
T1    | Проверка доступа        |
T2    | Доступ есть ✅          |
T3    |                       | Проект удален
T4    | Подписка активна       | ❌ Клиент имеет доступ к удаленному проекту
```

**Сценарий:**
1. Клиент проверяет доступ к проекту
2. Доступ подтвержден
3. Проект удаляется ПОСЛЕ проверки
4. Клиент все еще имеет активную подписку

**Решение:**
- ✅ Проверять доступ при каждом broadcast
- ✅ При удалении проекта - отключить всех подписчиков
- ✅ Валидировать проект при каждом subscribe/unsubscribe

### 3. Race Condition при отправке логов с фильтрами

**Проблема:**
```
Время | Поток 1 (HTTP)          | Поток 2 (WebSocket)
------|-------------------------|----------------------
T1    | Новый лог создан       |
T2    | Получение подписок     | Клиент меняет фильтры
T3    | Фильтрация с старыми   | Новые фильтры сохранены
T4    | фильтрами              |
T5    | Broadcast              | Лог не прошел фильтры ❌
```

**Сценарий:**
1. Лог создается
2. Получаем список подписок с фильтрами
3. Клиент меняет фильтры ПЕРЕД broadcast
4. Лог фильтруется по старым фильтрам и не отправляется

**Решение:**
- ✅ Фильтровать на момент отправки (не кешировать состояние)
- ✅ Использовать атомарные операции для чтения подписок
- ✅ Проверять фильтры в момент broadcast, а не заранее

### 4. Race Condition при регенерации токена проекта

**Проблема:**
```
Время | Поток 1 (HTTP - создание лога) | Поток 2 (HTTP - регенерация токена)
------|----------------------------------|------------------------------------
T1    | Проверка токена (старый) ✅     |
T2    |                                 | Токен регенерирован
T3    | Лог сохранен                    |
T4    |                                 | Старый токен инвалидирован
T5    | Лог создан со старым токеном   | ❌ Лог создан после регенерации
```

**Сценарий:**
1. Приложение отправляет лог со старым токеном
2. Токен проверен и валиден
3. Токен регенерируется ПОСЛЕ проверки
4. Лог сохраняется, но токен уже недействителен

**Решение:**
- ✅ **Не критично:** Лог уже создан, цель достигнута
- ✅ **Grace period:** Дать старым логам завершиться (например, 1-2 секунды)
- ✅ **Логирование:** Записывать события регенерации токена

### 5. Race Condition при удалении проекта и активных логах

**Проблема:**
```
Время | Поток 1 (HTTP - создание лога) | Поток 2 (HTTP - удаление проекта)
------|----------------------------------|------------------------------------
T1    | Проверка projectId ✅           |
T2    |                                 | Проект удаляется
T3    | Лог сохраняется                |
T4    |                                 | Проект удален
T5    | Лог создан для удаленного       | ❌ Лог сирота или constraint error
```

**Сценарий:**
1. Лог отправляется для проекта
2. Проект удаляется ПЕРЕД сохранением лога
3. Constraint violation или лог сирота

**Решение:**
- ✅ **CASCADE DELETE:** Prisma уже настроен с `onDelete: Cascade`
- ✅ **Транзакции:** Проверка существования проекта в транзакции
- ✅ **Ошибка:** Вернуть ошибку если проект не найден

### 6. Race Condition при одновременной очистке логов

**Проблема:**
```
Время | Поток 1 (Scheduled Task) | Поток 2 (HTTP - запрос логов)
------|---------------------------|------------------------------
T1    | Начало очистки            |
T2    | Удаление старых логов      | Запрос логов
T3    |                           | Логи уже удалены ❌
T4    | Очистка завершена         |
```

**Сценарий:**
1. Scheduled task начинает удалять старые логи
2. Пользователь запрашивает логи в том же временном диапазоне
3. Логи могут быть удалены во время запроса

**Решение:**
- ✅ **Транзакции:** Использовать транзакции для атомарной очистки
- ✅ **Locks:** Использовать SELECT FOR UPDATE для блокировки
- ✅ **Время выполнения:** Выполнять очистку в ночное время (меньше нагрузка)
- ✅ **Постепенная очистка:** Удалять порциями, а не все сразу

### 7. Race Condition при множественных подписках одного клиента

**Проблема:**
```
Время | Поток 1                       | Поток 2
------|--------------------------------|------------------------------
T1    | subscribe(project1, filters1)  |
T2    | subscribe(project2, filters2)  | Новый лог для project1
T3    |                               | Broadcast с filters2 ❌
T4    | Лог не прошел фильтры         |
```

**Сценарий:**
1. Клиент подписывается на проект1 с фильтрами
2. Клиент подписывается на проект2 с другими фильтрами
3. При broadcast используется неправильный набор фильтров

**Решение:**
- ✅ **Раздельные подписки:** Хранить фильтры для каждой подписки отдельно
- ✅ **Map структура:** `Map<clientId, Map<projectId, filters>>`
- ✅ **Проверка при broadcast:** Использовать правильные фильтры для каждого проекта

## 📋 Решения для реализации

### 1. Атомарные операции

**Для проверки доступа:**
```typescript
// Использовать транзакции Prisma
await prisma.$transaction(async (tx) => {
  const project = await tx.project.findUnique({
    where: { id: projectId },
  });
  
  if (!project) {
    throw new NotFoundException('Project not found');
  }
  
  // Сохранить лог в той же транзакции
  const log = await tx.log.create({...});
  return log;
});
```

### 2. Optimistic Locking

**Для регенерации токена:**
```typescript
// Проверка версии проекта
const project = await projectRepository.findUnique({ 
  where: { id, token: oldToken } 
});

if (!project || project.version !== expectedVersion) {
  throw new ConflictException('Token was regenerated');
}
```

### 3. Idempotency Keys

**Для создания логов (опционально):**
```typescript
// Предотвратить дублирование
interface CreateLogDto {
  // ...
  idempotencyKey?: string; // UUID от клиента
}

// Проверить наличие ключа
const existing = await logRepository.findUnique({
  where: { idempotencyKey },
});

if (existing) {
  return existing; // Вернуть существующий
}
```

### 4. Graceful Shutdown для WebSocket

**При удалении проекта:**
```typescript
async deleteProject(projectId: string) {
  // 1. Отключить всех подписчиков
  const room = this.io.to(`project:${projectId}`);
  room.emit('project:deleted', { projectId });
  room.disconnectSockets(true);
  
  // 2. Удалить проект (CASCADE удалит логи)
  await this.projectRepository.delete({ id: projectId });
}
```

### 5. Batch Operations для очистки

**Постепенная очистка через NestJS Scheduler:**
```typescript
// Реализация через @nestjs/schedule
// См. docs/SCHEDULER_SETUP.md

async cleanupOldLogs() {
  const BATCH_SIZE = 1000;
  let deleted = 0;
  
  do {
    deleted = await prisma.log.deleteMany({
      where: {
        timestamp: {
          lt: subDays(new Date(), 30),
        },
      },
      take: BATCH_SIZE,
    }).count();
    
    // Пауза между батчами
    await new Promise(resolve => setTimeout(resolve, 100));
  } while (deleted === BATCH_SIZE);
}
```

**Примечание:** Все CRON задачи реализованы через код (@nestjs/schedule), не через SQL функции.
